# dev-container-feature-development

Dev Container Features 開発用のエージェント プラグイン。

## 利用の前提

- このプラグインで作る Feature リポジトリは、AI エージェントだけが編集すると想定する。スクリプトは想定した文脈（CI のワークフローや、スキルからの呼び出し）でのみ実行され、単体で手動実行されることはないと想定する。
- エージェントの誤りは、スキルとエージェント（`feature-reviewer` など）の指示で防ぐ。レビューでは、エージェントが指示に従えば正しく作業できるかを基準にし、人が手で編集した場合や手動で実行した場合の問題は扱わない。
- ワークフロー雛形のスクリプト（`targets` ジョブや集約ジョブの判定など）の実行時の振る舞いを検査する CI ハーネスは設けない。壊れ方は無数に考えられ、一部だけを検査しても守れないため。

## 対象プラットフォーム

Feature 実行環境となる Dev Container の OS とアーキテクチャについて。

- どのディストリビューション、リリース、アーキテクチャをサポートするかは、プラグインではなく、プラグインを使う各 Features リポジトリが決める（aetos382/agent-plugins#22）。
  - 正本は、そのリポジトリの CI ワークフローのテスト ジョブが呼ぶ再利用可能ワークフロー（通常は `test-feature.yaml`）の `baseImage` の一覧と、`RUNNERS` のキーである。「サポート対象とは、そのリポジトリの CI がテストしているもの」という定義になる。一覧のファイルを別に設けない。
  - サポートするプラットフォームの一覧は、Feature ごとには持たない。新しい LTS が出るたびに全 Feature を直すことになり、ほとんどが同じ内容の写しになるためである。アーキテクチャを Feature ごとに `architectures` で絞れるのは、upstream にビルドが無いアーキテクチャが Feature ごとに違うからで、ディストリビューションにはその事情がほとんど無い。
  - スキルとエージェントは、一覧をリポジトリのワークフローから読む。プラグインの文書の指示に、リポジトリがサポートするリリース、イメージ名、アーキテクチャを決まりとして書かない。例の中に書くのはよい。プラグインの範囲（下の項目）は、これとは別である。
  - `init-repository` は、既存のリポジトリの `baseImage` と `RUNNERS` を雛形に合わせて書き換えない。雛形の初期値との差を、計画に情報として挙げるだけである。一覧を変えるときに一緒に直すもの（シナリオのイメージ、各 Feature の `install.sh` の `uname -m` 分岐と `NOTES.md`、ジョブの `architectures`）は、`supported-platforms.md` の「Changing a repository's lists」に書き、`feature-reviewer` が一覧の変更時に全 Feature を照らす。
- プラグインに残すのは原則と初期値である。原則は `plugins/dev-container-feature-development/skills/feature-authoring/references/supported-platforms.md` に書く。
  - プラグインの決まり、雛形、例が扱うのは、Debian と Ubuntu の amd64 と arm64 で、GitHub ホステッド ランナーでテストするものだけである。リポジトリがその外に出る（一覧に Alpine のイメージを入れ、`install.sh` に `apk` の分岐を書くなど）のは自由だが、その部分はリポジトリのもので、プラグインの決まりは及ばない。スキルは、ユーザーに頼まれたときと、リポジトリが一覧に入れているときに、一般的な知識で書き、`feature-reviewer` は指摘しない。範囲の外を見つける検査や、範囲の外のための決まりは設けない。リポジトリの裁量を大きくしつつ、そのためにプラグインを複雑にしないためである。
  - サポートと呼べるのは、CI でテストしているものだけである。`NOTES.md` には、CI でテストしているディストリビューション、リリース、アーキテクチャを書く。
  - ベース イメージのタグは、リリースで固定する（digest を足すのはよい）。`RUNNERS` のランナーのラベルも、リリースで固定する。Feature を実行しないジョブ（`targets` や集約ジョブ）は `ubuntu-latest` でよい。
  - 一覧には `mcr.microsoft.com/devcontainers/base` のイメージを 1 つ以上含める。Feature を入れる先のほとんどがこのイメージから派生していること、非 root の `vscode` ユーザーで `_REMOTE_USER` の経路を試せることの 2 つが理由である。
  - 各アーキテクチャは、そのアーキテクチャのネイティブ ランナーでテストする。
- 初期値は、`init-repository` の雛形 `plugins/dev-container-feature-development/skills/init-repository/assets/workflows/test-feature.yaml` の `baseImage` と `RUNNERS` にだけ書く。選び方は `supported-platforms.md` の「Initial values」にだけ書き、ここや README には写さない。これは規則ではなく、妥当な選択の 1 つである。
  - プラグイン内の例に書くイメージ名、リリース番号、アーキテクチャは、雛形の初期値から選ぶ。CI ランナー名は雛形の `RUNNERS` 以外に書かない。
  - 例と雛形が一致しているかは、CI では検査しない。例の値は説明のためのもので、食い違ってもプラグイン利用者のリポジトリは壊れない（例をまねたシナリオは、そのリポジトリの一覧を見る `feature-reviewer` が指摘する。CI は、シナリオのイメージが一覧にあるかを検査しない）。食い違いが生まれるのは雛形の初期値を変えたときだけなので、そのときに `/update-initial-platforms` スキルの手順で合わせる。
  - 上流の新しいリリース（Ubuntu LTS、Debian stable、`devcontainers/base` の新しいイメージやメジャー バージョン、GitHub ホステッド ランナーの新しい Ubuntu 版や新しいアーキテクチャ）は自動では検出しない。気づいたら `/update-initial-platforms` スキルで初期値と例を更新する。ただしアーキテクチャは、スキルが差を報告し、足すか外すかはユーザーが決める。決めたら、同じスキルの手順で直す。既存のリポジトリが新しいリリースにどう追従するか（Renovate の custom manager など）は、各リポジトリが決める。
- 目的が一部のディストリビューションでしか意味を持たない Feature（Ubuntu にしかパッケージを配らない Launchpad の PPA を足すものなど）は、他のディストリビューションで働かなくてよい。既定のオプションでは何もせず、対象外のディストリビューションでオプションを有効にしたら失敗させる。ベース イメージは `devcontainer.json` で決まり、誰がビルドしても同じ結果になるので、止めてよい。1 つのディストリビューション専用の Feature のために、`baseImage` の一覧を分けない。

## 対象アーキテクチャ

- リポジトリの `RUNNERS` のキーにあるアーキテクチャをサポートし、CI でそれぞれのネイティブ ランナーでテストする。CI でテストできないアーキテクチャはサポートしない。
- 各 Feature は対象アーキテクチャを、CI ワークフロー（通常は `ci.yaml`）の `test-<id>` ジョブの `architectures` に明示する。再利用可能ワークフロー `test-feature.yaml` の `architectures` 入力は必須とし、既定値は設けない。リポジトリが `RUNNERS` にアーキテクチャを足したときに、upstream にビルドがない Feature まで黙ってテスト対象に広がるのを防ぐため。
- CI ワークフローは Feature ごとのテスト ジョブを YAML に書き並べる。`src/` から Feature を列挙して matrix に展開する方式は採らない。matrix には 1 つあたり 256 ジョブの上限があり、Feature 数 × アーキテクチャ数 × baseImage 数ですぐに達するため。ジョブや集約ジョブの `needs` の書き漏れは CI では検出せず、`feature-reviewer` エージェントで検出する（「利用の前提」を参照）。
- upstream がビルドを公開していないアーキテクチャに限り、Feature の対象から外してよい。そのアーキテクチャでは失敗させる。何もせずに成功させると、ツールが入っていないコンテナーができ、Feature 利用者は後からコマンドが無いことで気づくためである。
- Feature のすることがそのアーキテクチャでは意味を持たない場合（書き換える対象が無いなど）は、失敗させずに、警告を出して何もしない。同じ `devcontainer.json` を複数のアーキテクチャでビルドするので、失敗させると片方の Feature 利用者だけがビルドできなくなるためである。この経路も CI でテストする。
  - 2 つの場合は、何もしなくても Feature 利用者が期待する状態と変わらないかどうかで見分ける。
- 「テストされている」とは CI でテストされていることを指す。手元のマシンでのテストは、そのマシンのアーキテクチャしか確認できないので、根拠にしない。

## CI ワークフローと集約ジョブ

- CI ワークフローは、このプラグインが所管するワークフロー ファイルである。行 `# dev-container-feature-development: ci` を持つことで見分ける。ファイル名や、実行している内容では見分けない。リポジトリに 1 つだけ置く。
  - この行を持たないワークフローは、同じテストや検査を実行していても CI ワークフローではない。以前のバージョンが書いた `test.yaml` と `validate.yaml` も同じである。`init-repository` は、既存のワークフローを CI ワークフローに取り込まず、改名も統合もしない。
  - この行を持つワークフローが無いときは、`init-repository` が雛形から新しく作る。これを既定とし、計画の承認でユーザーに確かめる。同じ内容を実行する既存のワークフローは残るので、二重に走ることを計画で伝える。消すのはユーザーである。
  - 既存のワークフローがあるのにどれもこの行を持たないときは、ユーザーに尋ねず、Git の履歴（`git log -S`）でこの行が失われたのかどうかを調べる。既定の名前（`ci.yaml`、`ci.yml`）を先に見る。今もあるファイルから失われていたら、その行を戻す。
- CI ワークフローには、このプラグインが管轄するジョブ（`validate`、`shellcheck`、`test-<id>`、`test-global`）を集約するジョブを 1 つ置く。Feature を足すたびにチェックの名前が増えるので、1 つのチェックで全体の成否が分かるようにするためである。
- 集約ジョブの名前は固定しない。雛形の `ci-passed` は初期値であり、スキルとエージェントは名前を前提にしない。集約ジョブは、ジョブ ID の直上にあるコメント行 `# dev-container-feature-development: aggregate job` で見つける。`needs` の中身では見つけない。Feature がまだ無いリポジトリでは、`needs` にテスト ジョブが無いためである。
- 2 つの行は `init-repository` だけが書く。雛形では、それぞれの上に「この行を編集、移動、削除しない」というコメントを置く。他のスキルとエージェントは、この行を足しも変えもしない。
- スキルとエージェントが編集し、確かめ、読むワークフローは、CI ワークフローと、そのテスト ジョブが呼ぶ再利用可能ワークフロー（通常は `test-feature.yaml`）だけである。行を持たないワークフローは、Feature をテストしているものでも、編集せず、確かめず、ベース イメージの一覧や CI の結果の読み取りにも使わない。一覧を読む先の順序と条件は、`supported-platforms.md` の「Where a repository's platforms are defined」にだけ書き、スキルとエージェントはそこを参照する。要点は、CI ワークフローにテスト ジョブがあればそれが呼ぶワークフロー、テスト ジョブが無く `.github/workflows/test-feature.yaml` があればそのファイル、それ以外（CI ワークフローが無いときを含む）は雛形の初期値で、初期値を使うときはリポジトリの一覧ではないことをユーザーに伝える。CI ワークフローが無くても、`run-feature-tests` はこの初期値でローカルの実行を続ける。CI でサポートを保証できないことと、手元で動くかを確かめられることは別だからである。
- 行が見つからないときは、黙って飛ばさない。スキル（`feature-testing`、`new-feature`）はユーザーに伝えて `init-repository` を勧める。ユーザーが断ったら、Feature のファイル（`src/<id>/`、`test/<id>/`）だけを扱い、その Feature が CI でテストされないことを伝える。エージェント（`feature-reviewer`）は、確かめられなかったことを High として報告する。
- 2 つの行の文言は、雛形、`init-repository`、`feature-testing`、`new-feature`、`feature-reviewer` で一致させる。変えるときは、すべてを同時に変える。
- CI ワークフローの外にある集約ジョブは、リポジトリのものである。改名も統合もせず、行も足さない。新しく作る集約ジョブのジョブ ID は、他のワークフローのジョブと重ならないようにする。同じ名前のチェックが複数あると、必須チェックの結果が曖昧になるためである。
- 集約ジョブを必須チェックにするかどうか、ruleset を使うかどうかは、リポジトリが決める。スキルや雛形のコメントでは、必須にしている場合の注意として書き、前提にしない。
- 「頼まれていないのにジョブを改名しない」は、どのリポジトリにも当てはまる作法であり、このプラグインの決まりとしては書かない。書くのは、スキルが自分でジョブを改名または削除する手順（Feature の改名と削除）だけである。そこでは、先に ruleset の必須チェックを調べ、旧名が使われていればユーザーに伝える。ruleset は変更しない。
- 確かめるのは、このプラグインが管轄するジョブが、集約ジョブの `needs` に漏れなくあることだけである。

## 開発方針

Feature に含まれるスクリプトの書き方について。

- 依存パッケージは `apt-get` で入れる。他のパッケージ マネージャーの分岐は、プラグインの範囲の外である（「対象プラットフォーム」を参照）。
  - 依存パッケージを入れる必要があるのに `apt-get` が無いときは、そのことと、Debian か Ubuntu のイメージが要ることをメッセージに出して、終了コード 1 で終了する。`apt-get` が無いことと、`apt-get` の実行の失敗を、メッセージで見分けられるようにするためである。足りない依存パッケージの一覧は出さなくてよい。
  - `apt-get` があるかは `command -v apt-get` で確かめ、`/etc/os-release` では確かめない。
- Feature が必要とする依存関係は `src/<feature>/NOTES.md` に明記する。
- テストはリポジトリの `baseImage` の一覧のすべてで行う。
- [nanolayer](https://github.com/devcontainers-extra/nanolayer) は使わない。
- Feature が同じイメージで 2 回実行されることは、起こるものとして扱う。事前ビルドしたイメージに同じ Feature を書いた場合と、`dependsOn` で取り込まれたものと Feature 利用者が書いたものとでオプションや版が違う場合に、実際に 2 回実行される（devcontainer CLI 0.89.0 で確認）。
  - 2 回目の結果は、Feature が何を触るかで決める。自分で作る設定やファイルは後勝ち、一覧への追加は積み上げ、オプションから再現できないものは残す、とする。
  - すでにある設定をその場で書き換える Feature は、期待した入力が無ければ、警告を出して何もしない。原因が以前の自分の実行か、別の手段での設定かは見分けさせない。どちらでも Feature 利用者に見えるのは警告で、見分けるには以前の実行を記録する仕組みが要るためである。
  - 指定したオプションが効かないのに、何も言わずに成功することだけは認めない。
  - `dependsOn` の経路では、どちらが後に実行されるかを Feature 自身も Feature 利用者も決められない。これは Feature の側では直せないので、規則の対象にしない。
