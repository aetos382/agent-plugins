# devcontainer features test

Reference for the test command of the [Dev Container CLI](https://github.com/devcontainers/cli) (`npm install -g @devcontainers/cli`). The upstream documentation is <https://github.com/devcontainers/cli/blob/main/docs/features/test.md>.

## Flags

| Flag | Meaning |
|---|---|
| `-p, --project-folder <dir>` | Folder containing `src/` and `test/`. Defaults to `.`. |
| `-f, --features <id...>` | Features to test. Omit to test all. |
| `-i, --base-image <image>` | Base image for auto-generated and duplicate tests. Ignored by scenarios. Default `ubuntu:focal`, which is obsolete; always pass it. |
| `-u, --remote-user <user>` | Remote user for auto-generated tests. |
| `--skip-autogenerated` | Skip `test.sh`. |
| `--skip-scenarios` | Skip `scenarios.json`. |
| `--skip-duplicated` | Skip `duplicate.sh`. |
| `--global-scenarios-only` | Run only `test/_global`. Cannot be combined with `-f`. |
| `--filter <text>` | Run only scenarios whose name contains the text. |
| `--preserve-test-containers` | Keep containers after the run for inspection. |
| `--log-level debug\|trace` | More build output. |

Typical invocations:

```bash
# Default options on one base image, including duplicate.sh if present.
devcontainer features test -p . -f mytool --skip-scenarios -i debian:12

# All scenarios of one Feature, once each.
devcontainer features test -p . -f mytool --skip-autogenerated --skip-duplicated

# One scenario.
devcontainer features test -p . -f mytool --skip-autogenerated --skip-duplicated --filter pinned_version
```

## How a scenario is assembled

For each scenario the CLI creates a temporary directory containing:

- `.devcontainer/devcontainer.json` — the scenario's value from `scenarios.json`.
- `.devcontainer/<id>/` — a copy of `src/<id>/` for every Feature in the repository, which is why bare IDs work in `features`.
- The contents of `test/<id>/<scenario>/`, if that directory exists, copied into `.devcontainer/`.
- All files from `test/<id>/`, plus `dev-container-features-test-lib`, in the workspace folder, where the assertion script runs.

Because all of `test/<id>/` is copied, assertion scripts can read fixture files from the working directory.

## Test library

`dev-container-features-test-lib` is a Bash library; assertion scripts must be Bash.

| Function | Behavior |
|---|---|
| `check <label> <cmd> [args...]` | Runs the command. On non-zero exit, records the label as failed and returns 1. |
| `checkMultiple <label> <min> <expr...>` | Runs each expression (word-split, not through a shell) and passes when at least `<min>` succeed. |
| `reportResults` | Prints the result and exits 1 if any check failed, 0 otherwise. |

## Duplicate tests

When `test/<id>/duplicate.sh` exists and `--skip-duplicated` is not given, the CLI builds an image with the Feature installed twice: once with defaults and once with values it picks for each option (randomized only with `--permit-randomization`). The script receives the non-default values as `<OPTION>` and the defaults as `<OPTION>__DEFAULT`, both upper-cased. Duplicate tests run on the auto-generated base image.

## Debugging a failed build

1. Read the first error in the build log, not the last. `install.sh` output is prefixed with the Feature ID when it follows the authoring conventions.
2. Rerun only the failing case, with `--filter` for scenarios or `-i` for a base image, and `--log-level debug`.
3. Use `--preserve-test-containers`, then `docker ps -a` and `docker exec -it <container> bash` to inspect the result of a build that succeeded but whose assertions failed.
4. To iterate on `install.sh` without the CLI, run it directly in the base image with options as environment variables:

   ```bash
   docker run --rm -it -v "$PWD/src/mytool:/mnt/f:ro" debian:12 sh -c 'VERSION=1.2.3 sh /mnt/f/install.sh'
   ```

   `_REMOTE_USER` and related variables are not set this way; set them explicitly when the code path depends on them.
5. The CLI needs a working Docker daemon. When `docker info` fails inside a dev container, the container is missing Docker-in-Docker or the Docker socket.
