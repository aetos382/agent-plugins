# Run Dev Container Feature tests

Run the tests of one or more Features and report the results per Feature, base image, and scenario. Test authoring is covered by the `feature-testing` skill; consult it when a failure turns out to be a problem in a test.

Reply to the user in the language they use.

## Trust

Tests execute code from the repository: `install.sh` and scenario configurations run in containers that can request privileges or mounts, and negative tests contain shell commands. Run them only in a repository the user trusts. When the repository was cloned from a source the user has not mentioned owning or reviewing, say so and ask before running anything.

`docker run`, `docker exec`, and `docker rm` are deliberately not pre-approved, so the user sees each negative-test command before it runs.

## 1. Determine the targets

- When arguments are given, treat each as a Feature ID and confirm that `src/<id>/devcontainer-feature.json` exists.
- Otherwise, take the Features whose `src/<id>/` or `test/<id>/` changed relative to the default branch:

  ```bash
  git diff --name-only "$(git merge-base HEAD origin/HEAD)" -- src test
  git status --porcelain -- src test
  ```

  When `origin/HEAD` is not set, find the default branch with `gh repo view --json defaultBranchRef --jq .defaultBranchRef.name` and use `origin/<branch>`.

  Include `test/_global` when anything under it changed. When nothing changed, ask whether to test all Features.

## 2. Choose where to run

Run locally when both `command -v devcontainer` and `docker info` succeed. Otherwise use CI (section 5) and tell the user why local execution was not possible (no Docker daemon, or no Dev Container CLI; the CLI installs with `npm install -g @devcontainers/cli`).

## 3. Run locally

### Base images

Read the `baseImage` list from the matrix of the workflow that runs `devcontainer features test` (usually `.github/workflows/test.yaml`), so that local runs match CI. When no workflow exists, use the "CI base images" list in `${CLAUDE_PLUGIN_ROOT}/skills/feature-authoring/references/supported-distributions.md`.

When the workflow's list differs from that file, run with the workflow's list, and mention the difference in the report: the repository may not have been updated for a new release yet.

### Commands

For each target Feature, run these from the repository root, one command per Bash call, sequentially. Builds take minutes: set the Bash timeout to the maximum, or run in the background and wait for completion.

```bash
# Auto-generated test (and duplicate.sh, if present), once per base image.
devcontainer features test -p . -f <id> --skip-scenarios -i <image>

# Scenarios, once.
devcontainer features test -p . -f <id> --skip-autogenerated --skip-duplicated
```

When `test/_global` is a target, also run `devcontainer features test -p . --global-scenarios-only`.

When a run fails, keep going with the remaining images and scenarios, so that the report shows whether the failure is specific to one image.

### Negative tests

When `test/<id>/negative-tests.md` exists, execute every case in it. The file format and the rules for comparing output are defined in the `feature-testing` skill (section "Negative tests"); read that section first.

1. For each case, start a fresh container from the Setup command, translated into a detached container that keeps the image, platform, and mounts exactly as written:

   ```bash
   docker run -d --name "negtest-<id>-<case>" -v "$PWD/src/<id>:/mnt/f:ro" <image> sleep infinity
   ```

2. Confirm that the mount is visible: `docker exec "negtest-<id>-<case>" test -f /mnt/f/install.sh`. When it fails, the Docker daemon cannot see the working directory (typical with docker-outside-of-docker in a dev container). Report all negative tests as not run for that reason, and do not count them as failures.
3. Run the case's commands with `docker exec "negtest-<id>-<case>" sh -c '<case commands>'`, capturing stdout, stderr, and the printed exit status.
4. Check the described side effects with further `docker exec` commands.
5. Remove the container with `docker rm -f`, also after a failure.

A case whose section starts with `Run this case from the host.` has a complete `docker run` command instead. Run it only when it is a single `docker run` command whose image and mounts match the Setup command; otherwise show it to the user and ask before running it. When the case names an environment requirement, check it first and report the case as not run, with the reason, when the requirement is not met. For `Requires an x86_64 host.`, the Docker host must report `x86_64` in `docker info --format '{{.Architecture}}'`.

Never report a case that was not run as passed.

## 4. Analyze failures

For each failure, read the log from the first error rather than the last lines, and classify it:

| Class | Typical signs | Next step |
|---|---|---|
| `install.sh` bug | The Feature's own error message, a shell error, a wrong path | Point to the line and propose a fix |
| Test bug | Build succeeded, a `check` failed although the behavior is correct | Propose a fix to the test |
| Image difference | Fails on one base image only (missing package, different default) | Identify the difference and propose handling it in `install.sh` |
| Upstream or network | HTTP 5xx, 429, timeouts, TLS errors from a download | Rerun that case once; report as flaky when it then passes |
| Environment | Docker or CLI errors before `install.sh` runs | Report; not a Feature problem |

Rerun a single case with `--filter <scenario>` or `-i <image>`, adding `--log-level debug` or `--preserve-test-containers` when the log is not enough. The flags and debugging steps are in `${CLAUDE_PLUGIN_ROOT}/skills/feature-testing/references/test-cli.md`.

Present proposed fixes; apply them only when the user asks.

## 5. Use CI instead

1. Find the workflow that runs `devcontainer features test` under `.github/workflows/`, and note its triggers.
2. The CI result must correspond to the local `HEAD`. When the current branch has no upstream or the local branch is ahead of it, ask the user whether to push; do not push without approval.
3. Make sure a run exists for `HEAD`. Workflows created by the `init-repository` skill run on pull requests and on `workflow_dispatch`, not on pushes to topic branches:
   - When `gh pr view --json number` finds a pull request for the branch, the push triggers a run.
   - Otherwise, offer the user two options and wait for a choice: open a draft pull request, or dispatch the workflow on the branch with `gh workflow run <file> --ref <branch>`.
4. Find the run:

   ```bash
   gh run list --workflow <file> --branch "$(git branch --show-current)" --limit 10 --json databaseId,headSha,event,status,conclusion,url
   ```

   Pick the run whose `headSha` equals `git rev-parse HEAD`. When none exists yet, wait a few seconds and retry; report after about a minute without a run.
5. Wait with `gh run watch <id> --exit-status`. On failure, read `gh run view <id> --log-failed` and analyze as in section 4.
6. Negative tests cannot run in CI. Report them as not run.

## 6. Report

Summarize in a table: rows are Features × (each base image, each scenario, each negative case), columns are result and a one-line note. List failures with their classification and proposed fix below the table. Mention anything that was not run and why.
