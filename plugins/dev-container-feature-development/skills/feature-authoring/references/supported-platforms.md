# Supported platforms

Each Features repository decides which distributions and architectures it supports. This plugin sets the principles that the choice follows and the initial values that `init-repository` writes into a new repository, but no list of its own that a repository has to match.

## Where a repository's platforms are defined

The source of truth is the reusable workflow called by the test jobs of the CI workflow (usually `.github/workflows/test-feature.yaml`, and called `test-feature.yaml` below whatever its file name), and no other file:

- **Base images**: the `baseImage` matrix of its `autogenerated` job. Every Feature is tested on each of them, so the distributions and releases these images run are the ones the repository supports.
- **Architectures**: the keys of `RUNNERS` in its `targets` job. Each maps to the runner that tests that architecture natively. The `architectures` of a Feature's job in the CI workflow name only keys of `RUNNERS`, and `test-feature.yaml` rejects any other name.

The CI workflow is the workflow under `.github/workflows/` with the line `# dev-container-feature-development: ci`. Do not read the lists from any other workflow, even one that tests the Features. Find the reusable workflow by the first of these cases that applies:

1. **The CI workflow has test jobs.** Read the workflow that its test jobs (`test-<id>`, `test-global`) call in `uses`. Stop and tell the user, without falling back to the initial values, when the lists cannot be read from it: the file is missing, the test jobs call different workflows, `baseImage` is not a plain list of strings (for example built with `include` or an expression), or `RUNNERS` is missing or is not a JSON object whose values are strings.
2. **The CI workflow has no test job yet**, as right after `init-repository` created it, **and `.github/workflows/test-feature.yaml` exists.** Read that file, which `init-repository` writes together with the CI workflow. Stop as in the first case when the lists cannot be read from it.
3. **Otherwise**: the repository has no CI workflow, or has one with no test job and no `.github/workflows/test-feature.yaml`. A `.github/workflows/test-feature.yaml` without a CI workflow is not read, since no workflow of this plugin calls it. There is no list, nothing is tested by CI, and so nothing is supported. Where a list is still needed, such as to choose the image of a scenario or to run the tests locally, use the `baseImage` matrix and `RUNNERS` of the `init-repository` template (see "Initial values"), and tell the user that these are the initial values that `init-repository` would write, not the repository's lists.

Skills and agents read the lists from the workflow each time, and never write the releases, images, or architectures of a repository into their own instructions. Each Feature's `NOTES.md` does name them, as a description of what CI tests, so it is updated whenever the lists change (see "Changing a repository's lists").

## Principles

These hold for every repository, whatever it lists:

- **Scope.** This plugin's rules, templates, and examples cover Debian and Ubuntu on amd64 and arm64, tested on GitHub-hosted runners. A repository may go beyond them, for example with an Alpine image in its list and an `apk` branch in `install.sh`; such parts are the repository's own, and this plugin's rules do not apply to them.
- **Supported means tested by CI.** A platform counts as supported only when the CI workflow runs the Feature on it. A local run on the developer's machine does not count, because it covers only that machine's architecture and is not repeated on every pull request. Each Feature's `NOTES.md` names the distributions, releases, and architectures that CI tests it on.
- **Tags are pinned.** Each base image names a release (`debian:13`, not `debian:latest` or `debian`), optionally with a digest. Under a floating tag, an image moving to a new release would drop the old release from the tests without notice, and could fail every pull request at once. The runners in `RUNNERS`, which run the Features, are pinned in the same way, by a label that names a release rather than one such as `ubuntu-latest`. Moving to a newer release is a deliberate change of the repository. Jobs that do not run the Features, such as `targets` or the aggregate job, may use `ubuntu-latest`, since a new release there changes no tested platform.
- **At least one `mcr.microsoft.com/devcontainers/base` image.** Most dev containers that install Features are built on these images, so the Features must be shown to work there. They also have a non-root `vscode` user, which exercises the `_REMOTE_USER` path; the non-root scenarios of the `feature-testing` skill run on them.
- **Architectures on native runners.** Each architecture is tested on a runner of that architecture, not under emulation. An architecture without such a runner cannot be supported.
- **A Feature covers every listed base image and architecture.** A Feature works on every base image of the list. It leaves out an architecture of `RUNNERS` only when its upstream publishes no build for it. A Feature whose purpose has no meaning on some distributions follows "Features for one distribution" in the `feature-authoring` skill rather than narrowing the list.

The checks that can be made from the lists alone are: every base image pinned to a release, at least one `devcontainers/base` image, every GitHub-hosted runner in `RUNNERS` pinned to a release, and no two keys of `RUNNERS` mapped to the same runner. Whether a runner really is of its architecture cannot be seen from the lists or from a green CI run, since the tests of most Features pass on the wrong architecture too.

## Changing a repository's lists

Change the lists only when the user asks, and change everything that depends on them in the same pull request:

- **Removing a base image**: move every scenario `image`, and every `FROM` of a scenario's Dockerfile, that uses it to an image that stays, in `test/<id>/` and `test/_global/`. Keep at least one `mcr.microsoft.com/devcontainers/base` image.
- **Adding or removing a base image**: update the tested distributions in the Limitations of every Feature's `NOTES.md`. A Feature for one distribution also states which of the listed distributions it is for.
- **Adding a base image**: run the tests of every Feature on it (the `run-feature-tests` skill) before merging, since every Feature now claims support for it.
- **Removing an architecture from `RUNNERS`**: remove it from `architectures` of every job of the CI workflow, since `test-feature.yaml` fails a job that names it, and from the `uname -m` branches of `install.sh` and the Limitations of `NOTES.md` of each Feature, as "Changing the architectures of a Feature" in the `feature-testing` skill describes.
- **Adding an architecture to `RUNNERS`**: no Feature is tested on it until its job lists it. For each Feature, check that the upstream publishes a build for it, as the `new-feature` skill does, and extend the Feature as "Changing the architectures of a Feature" describes; leave it out only when there is no build.
- **Changing a runner**: nothing else depends on it. Confirm from GitHub's list of hosted runners that the new label is of that architecture. A green CI run does not show it. Then run the tests in CI.

Then have the `feature-reviewer` agent review the lists, and every Feature unless only a runner changed.

## Initial values

The template of the reusable workflow in the `init-repository` skill (`skills/init-repository/assets/workflows/test-feature.yaml` in this plugin) defines the initial values in its `baseImage` matrix and `RUNNERS`. The examples of this plugin's skills copy images and releases from them; in a repository, use the images of its own lists instead. `init-repository` writes the initial values into a repository that has no `test-feature.yaml` yet. From then on, they are the repository's own: `init-repository` does not change them in an existing repository, and only reports how they differ from the current initial values.

Last checked against upstream release information: 2026-09-18.

The initial values are chosen as follows. This is one reasonable choice, not a rule:

- **Ubuntu**: the latest LTS release and the one before it. This leaves an LTS release that still has standard support untested for about a year after the next one comes out. A repository that wants to keep it adds it to its own list.
- **Debian**: the current stable and oldstable releases.
- **`mcr.microsoft.com/devcontainers/base`**: the variant for each Ubuntu release above, each at the newest major version that has that variant. The Ubuntu and Debian variants are built from separate image definitions with their own version numbers, so a major version applies to one family only (for example, `3` is an Ubuntu major version and has no Debian variants). The variant for a new Ubuntu release appears weeks after the release; until it does, the list covers only the releases that have one.
- **Architectures**: chosen from the architectures for which GitHub offers standard hosted Linux runners to both public and private repositories.
- **Runners**: GitHub-hosted runners of the newest Ubuntu LTS release that GitHub offers for every architecture. Arm64 runners have no `latest` label in any case.

## Architecture names

The keys of `RUNNERS` are the architecture names that the `run-feature-tests` skill matches against `uname -m` of the Docker host, and that the `uname -m` branches of each Feature's `install.sh` correspond to (whatever names the upstream uses inside those branches). The `uname -m` value of each architecture within the plugin's scope:

| Architecture | `uname -m` |
|---|---|
| amd64 | `x86_64` |
| arm64 | `aarch64` |

Other architectures are outside the scope (see "Scope" above).
