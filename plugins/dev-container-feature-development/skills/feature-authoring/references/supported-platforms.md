# Supported platforms

Each Features repository decides which distributions and architectures it supports. This plugin sets the principles that the choice follows and the initial values that `init-repository` writes into a new repository, but no list of its own that a repository has to match.

## Where a repository's platforms are defined

The source of truth is the reusable workflow called by the test jobs of the CI workflow (usually `.github/workflows/test-feature.yaml`), and no other file:

- **Base images**: the `baseImage` matrix of its `autogenerated` job. Every Feature is tested on each of them, so the distributions and releases these images run are the ones the repository supports.
- **Architectures**: the keys of `RUNNERS` in its `targets` job. Each maps to the GitHub-hosted runner that tests that architecture natively. The `architectures` of a Feature's job in the CI workflow name only keys of `RUNNERS`, and `test-feature.yaml` rejects any other name.

The CI workflow is the workflow under `.github/workflows/` with the line `# dev-container-feature-development: ci`. Do not read the lists from any other workflow, even one that tests the Features. Find the reusable workflow in this order:

1. The workflow that the test jobs (`test-<id>`, `test-global`) of the CI workflow call in `uses`.
2. When the CI workflow has no test job yet, as right after `init-repository` created it, `.github/workflows/test-feature.yaml`, which `init-repository` writes together with the CI workflow.
3. When the repository has no CI workflow, or no `.github/workflows/test-feature.yaml` either, there is no list, and nothing is tested by CI, so nothing is supported. Where a list is still needed, such as to choose the image of a scenario or to run the tests locally, use the initial values below, and tell the user that these are not the repository's lists and that `init-repository` creates them.

Do not write the releases, images, or architectures of a repository into skills, agents, or Features' `NOTES.md` as rules. Read them from the workflow each time, so that a change to the workflow is the only change needed.

## Principles

These hold for every repository, whatever it lists:

- **Supported means tested by CI.** A platform counts as supported only when the CI workflow runs the Feature on it. A local run on the developer's machine does not count, because it covers only that machine's architecture and is not repeated on every pull request.
- **Untested is said so.** Each Feature's `NOTES.md` names the distributions it is tested on and says that others are not tested. Other distributions are supported only when that costs no more than a package-manager branch, and even then they are untested.
- **Tags are pinned.** Each base image names a release (`debian:13`, not `debian:latest` or `debian`), optionally with a digest. Under a floating tag, an image moving to a new release would drop the old release from the tests without notice, and could fail every pull request at once. The runners are pinned in the same way, by a label that names an Ubuntu release rather than `ubuntu-latest`. Moving to a newer release is a deliberate change of the repository.
- **At least one `mcr.microsoft.com/devcontainers/base` image.** Most dev containers that install Features are built on these images, so the Features must be shown to work there. They also have a non-root `vscode` user, which exercises the `_REMOTE_USER` path; the non-root scenarios of the `feature-testing` skill run on them.
- **Architectures on native runners.** Each architecture is tested on a runner of that architecture, not under emulation. An architecture without such a runner cannot be supported.
- **A Feature covers all of them.** A Feature works on every base image of the list. It leaves out an architecture of `RUNNERS` only when its upstream publishes no build for it. A Feature whose purpose has no meaning on some distributions follows "Features for one distribution" in the `feature-authoring` skill rather than narrowing the list.

## Initial values

The `test-feature.yaml` template of the `init-repository` skill (`skills/init-repository/assets/workflows/test-feature.yaml` in this plugin) holds the initial values, and it is the only place in this plugin that lists them. `init-repository` writes them into a repository that has no `test-feature.yaml` yet. From then on, they are the repository's own: `init-repository` does not change them in an existing repository, and only reports how they differ from the current initial values.

The initial values are chosen as follows. This is one reasonable choice, not a rule:

- **Ubuntu**: the latest LTS release and the one before it. This leaves an LTS release that still has standard support untested for about a year after the next one comes out. A repository that wants to keep it adds it to its own list.
- **Debian**: the current stable and oldstable releases.
- **`mcr.microsoft.com/devcontainers/base`**: the variant for each Ubuntu release above, each at the newest major version that has that variant. The Ubuntu and Debian variants are built from separate image definitions with their own version numbers, so a major version applies to one family only (for example, `3` is an Ubuntu major version and has no Debian variants). The variant for a new Ubuntu release appears weeks after the release; until it does, the list covers only the releases that have one.
- **Architectures**: amd64 and arm64, the architectures for which GitHub offers hosted Linux runners.
- **Runners**: the newest Ubuntu LTS release that GitHub offers for every architecture. Arm64 runners have no `latest` label in any case.

The images named in the examples of this plugin's skills are taken from the initial values. In a repository, use the images of its own list instead.

## Architecture names

The keys of `RUNNERS` are the names that `uname -m` maps to in `install.sh` and that the `run-feature-tests` skill matches against the Docker host. The initial values use these:

| Architecture | `uname -m` |
|---|---|
| amd64 | `x86_64` |
| arm64 | `aarch64` |
