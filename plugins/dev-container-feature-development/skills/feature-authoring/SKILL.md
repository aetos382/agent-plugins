# Authoring Dev Container Features

A Dev Container Feature is a directory `src/<id>/` containing `devcontainer-feature.json` (metadata) and `install.sh` (the entrypoint run as root during the image build). This skill defines how Features in this style of repository are written. Apply it whenever a file under `src/<id>/` is created or changed.

## Repository layout

```
src/<id>/
  devcontainer-feature.json   # metadata; "id" must equal the directory name
  install.sh                  # entrypoint, run as root at build time
  NOTES.md                    # hand-written; appended to the generated README
  README.md                   # generated at release time; never edit by hand
  (other files)               # packaged together with install.sh
test/<id>/
  test.sh                     # default options, run on every base image
  scenarios.json, <name>.sh   # option and environment scenarios
  <name>/                     # extra build files for a scenario (e.g. a Dockerfile)
  duplicate.sh                # idempotency test (optional)
  negative-tests.md           # failure cases the CLI cannot express
test/_global/                 # scenarios spanning several Features (optional)
```

The `feature-testing` skill describes each test file.

Only files inside `src/<id>/` are packaged. Anything `install.sh` needs at build time (helper scripts, config templates, entrypoint scripts) must live there and be referenced relative to the script's own directory.

`README.md` is regenerated by `devcontainers/action` from `devcontainer-feature.json` plus `NOTES.md`. Put all hand-written documentation in `NOTES.md`.

## Supported distributions

Every Feature must work on the latest two Ubuntu LTS releases and on Debian stable and oldstable, and CI tests all of them, plus `mcr.microsoft.com/devcontainers/base` images with a non-root user. Read `references/supported-distributions.md` for the current releases and image names; it is the single source of truth, so never take release numbers from memory or from other files.

Other distributions are supported only when doing so costs no more than a package-manager branch. Never state or imply support that has not been tested: `NOTES.md` must say that only the supported distributions are tested.

## Dependency policy

- Install missing dependencies with `apt-get`. Probe for each command first (`command -v`) and install only what is missing, so that images that already have the tools are untouched.
- When `apt-get` is unavailable and a required dependency is missing, print an error naming every missing dependency and `exit 1`. Do not attempt `apk`, `dnf`, or other package managers unless the Feature explicitly supports that distribution.
- After `apt-get install`, remove `/var/lib/apt/lists/*` to keep the layer small.
- Always pass `DEBIAN_FRONTEND=noninteractive` and `--no-install-recommends`.
- List every runtime and build-time dependency in `NOTES.md`, including which ones are installed automatically and which ones must be preinstalled on images without `apt-get`.
- Do not use [nanolayer](https://github.com/devcontainers-extra/nanolayer) or other install helpers that fetch code at build time. Keep the install logic in the Feature's own scripts.

## Writing install.sh

Follow these rules. Detailed patterns with code are in `references/install-script.md`.

1. **Shell.** Write POSIX `sh` (`#!/bin/sh`, `set -eu`) unless the script genuinely needs Bash; POSIX sh has no `pipefail`, so never pipe a command whose failure matters. When Bash is required, use `#!/bin/bash` and `set -euo pipefail`, and note in `NOTES.md` that Bash must exist on images without `apt-get`.
2. **Root check.** Fail early with a clear message when `id -u` is not 0.
3. **Options.** Each option arrives as an upper-cased environment variable (`myOption` → `MYOPTION`, non-word characters become `_`). Read with a default that matches `devcontainer-feature.json`, e.g. `VERSION="${VERSION:-latest}"`. Validate values before use; free-form strings must never reach a path or command unchecked.
4. **Messages.** Prefix every message with the Feature ID (`<id>: ...`) and send errors to stderr. State what failed and what the user can do about it.
5. **Architecture.** Detect with `uname -m`, not `dpkg --print-architecture`, so detection does not depend on Debian tooling. Fail with a message for unsupported values.
6. **Downloads.** Use `curl -fsSL --retry 3`. Verify every downloaded artifact against a checksum file or signature that the upstream publishes separately from the artifact. Prefer signatures, and pin the signing key's fingerprint in the script. A checksum file from the same release protects against corrupted downloads but not against a compromised release; when that is all the upstream offers, use it and say so in `NOTES.md`. When a version is pinned, confirm the installed binary reports that version.
7. **Temporary files.** Create them with `mktemp -d` and remove them in an `EXIT` trap.
8. **Users.** The script runs as root. Use `_REMOTE_USER` / `_REMOTE_USER_HOME` for per-user setup, `chown` what is created in a user's home, and never assume the user is `root` or `vscode`.
9. **Idempotency.** Running the script twice, or with different options, must not fail or corrupt the result. Check before appending to files, use `ln -sfn`, and prefer writing whole files over editing.
10. **Summary line.** End with one line stating what was installed or configured, including the resolved version.

Comments explain *why*, not *what*. Write them in American English.

## Writing devcontainer-feature.json

- Required: `id` (lowercase, equals the directory name), `version` (SemVer), `name`.
- Always set `description`, `documentationURL` (`https://github.com/<owner>/<repo>/tree/main/src/<id>`), and `licenseURL`.
- Give every option a `type` (`string` or `boolean`), a `default`, and a `description`. Use `enum` for closed sets and `proposals` for suggestions.
- Never accept secrets as options: option values are committed in the user's `devcontainer.json`, appear in build logs, and are written to `devcontainer-features.env`, which can persist in an image layer depending on how the image is built. Document how to pass secrets at runtime (`remoteEnv`, Codespaces secrets) in `NOTES.md` instead.
- Use `installsAfter` for soft ordering (e.g. after `ghcr.io/devcontainers/features/common-utils`) and `dependsOn` only for hard requirements, since `dependsOn` pulls the dependency in.
- A new Feature starts at `1.0.0` unless the user asks otherwise. Do not bump `version` while developing; the `release` skill decides the bump.

The full property list, lifecycle hooks, `containerEnv`, `mounts`, `entrypoint`, and the `${devcontainerId}` variable are covered in `references/feature-json.md`.

## Writing NOTES.md

Use these sections, omitting any that would be empty:

- `## How it works` — what the script installs or changes, where, and why that method was chosen.
- `## Requirements` — dependencies; what `apt-get` installs automatically; what images without `apt-get` must provide.
- `## Limitations` — tested distributions (from `references/supported-distributions.md`) and the statement that other distributions are untested; supported architectures; known gaps.

`examples/NOTES.md` shows the expected shape.

## After changing a Feature

1. Run `shellcheck` on every changed script when it is available.
2. Update tests under `test/<id>/` for behavior changes; see the `feature-testing` skill.
3. Offer to run the `run-feature-tests` skill, and the `feature-reviewer` agent for a policy review.
